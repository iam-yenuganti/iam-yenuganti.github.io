Private AKS Without Breaking Your Deployments

9 min read · 23 September 2026

Locking down an AKS cluster is easy. Locking it down so it still upgrades, pulls images and lets your pipeline deploy is where teams get stuck. This is the setup I use for production clusters that handle regulated data, and the places it usually breaks.

Make the API server private

A private cluster puts the Kubernetes API server behind a private IP in your network. You have two ways to do that: the original Private Link based private cluster, or API Server VNet Integration, which projects the API server into a delegated subnet so nodes talk to it directly. Both keep node to API server traffic on the private network.

Even a private cluster gets a public DNS name for the API server by default. It doesn't expose the API, but I still remove it with --disable-public-fqdn when the cluster lives in a hub and spoke network with proper private DNS.

az aks create \
  --resource-group rg-app-prod \
  --name aks-app-prod \
  --enable-private-cluster \
  --disable-public-fqdn \
  --private-dns-zone system \
  --outbound-type userDefinedRouting \
  --network-plugin azure \
  --os-sku AzureLinux \
  --enable-workload-identity --enable-oidc-issuer

The first thing that breaks is your pipeline. GitHub-hosted runners and Microsoft-hosted agents can't reach a private API server. Run a self-hosted runner in a network peered to the cluster, or use az aks command invoke for occasional admin work. Command invoke goes through the Azure API, so lock down who holds the runcommand permission.

Send egress through the firewall

By default an AKS cluster has unrestricted outbound internet access. To control it, set the outbound type to userDefinedRouting, put a route table on the node subnet that sends 0.0.0.0/0 to Azure Firewall, and allow only what the cluster needs.

You can't do this with network security groups alone. AKS dependencies are defined by FQDN, and the IP addresses behind them change. Azure Firewall application rules can filter by FQDN, and the AzureKubernetesService FQDN tag covers the core set. The required list includes:

  • mcr.microsoft.com and *.data.mcr.microsoft.com for system images
  • management.azure.com and login.microsoftonline.com for the Azure API and Entra sign-in
  • packages.microsoft.com and packages.aks.azure.com (which is replacing acs-mirror.azureedge.net) for packages and Kubernetes binaries

Private clusters don't need the *.hcp.<region>.azmk8s.io rule, because node to API server traffic stays private. Add your workloads' own destinations on top, one rule at a time, with a ticket behind each one.

Or go further: a network isolated cluster

If your requirement is "no egress at all unless we say so", AKS now has a better answer than maintaining firewall rules for its own dependencies. A network isolated cluster uses outbound type none (or block, still in preview) and sets the bootstrap artifact source to Cache. AKS then pulls its images and binaries from a private Azure Container Registry cache over a private endpoint. The cache fetches from Microsoft Artifact Registry on its own.

Creating the cluster, scaling node pools and running upgrades then need no outbound traffic from the cluster. You can let AKS manage the registry or bring your own. You still add egress back for whatever your applications call, through private endpoints where you can and the firewall where you can't.

Private endpoints and DNS

Everything the cluster depends on inside Azure should be reached privately: Container Registry, Key Vault, and Azure Monitor through an Azure Monitor Private Link Scope. Each one needs its private DNS zone, such as privatelink.azurecr.io, privatelink.vaultcore.azure.net and the cluster's own privatelink.<region>.azmk8s.io.

DNS is where most of my troubleshooting time goes. Keep the zones in the hub, link them to the networks that need them, and point spokes at the DNS Private Resolver. If your spokes use custom DNS, check the private cluster guidance on zone linking before you deploy; AKS needs the right permissions to link its zone, and the failure isn't obvious.

Inside the cluster

  • Workload identity instead of secrets for pods that call Azure services.
  • Network policies with a default deny, so a compromised pod can't reach everything else.
  • The Azure Policy add-on to block privileged containers and images from registries you don't trust.
  • Azure Linux 3 for node pools. Azure Linux 2.0 lost support on November 30, 2025.

What breaks, and how you'll notice

  • A DNS zone isn't linked. Nodes or your runner can't resolve the API server or the registry. Test name resolution from a pod and from the runner before anything else.
  • The firewall is missing an FQDN. Node provisioning or image pulls fail during an upgrade, not on day one. Run a node image upgrade in non-production before you trust the rule set.
  • The bootstrap registry is unreachable. On a network isolated cluster this shows up as error 211, OrasPullNetworkTimeoutVMExtensionError. It nearly always means the private link or DNS for the registry is wrong.

How I'd roll it out

  1. Build the hub pieces first: firewall, DNS resolver and private DNS zones.
  2. Create a private cluster in non-production with egress through the firewall.
  3. Put a self-hosted runner in a peered network and deploy through it.
  4. Run a scale-out and a node image upgrade. Fix whatever fails.
  5. Only then repeat it in production, and decide whether a network isolated cluster is worth it for you.
