Azure Landing Zones: The Decisions That Matter Before the First Workload

⏱ 8 min read 📅 September 5, 2025 ✍️ Srinivas Yenuganti
Azure Landing Zone Azure Policy Hub-Spoke Governance CAF

The most expensive Azure mistake I see isn't a badly sized VM. It's letting teams deploy workloads before the foundation exists. A few subscriptions get created by hand, everyone starts building, and a year later nobody can say which resources belong to whom, which ones face the internet, or why the bill doubled.

A landing zone fixes that by settling the boring decisions up front: how subscriptions are organized, where policy is applied, how networks connect and where logs go. Microsoft's Cloud Adoption Framework gives you a reference design. Here's how I apply it, and where I'd bend it.

Start with the management group hierarchy

Policy and RBAC assigned to a management group flow down to every subscription beneath it. That makes the hierarchy the most important choice in the whole landing zone, and the hardest one to change later.

The current Azure landing zone reference looks like this:

Tenant root group
└─ Intermediate root (your org prefix)
   ├─ Platform
   │  ├─ Security       Sentinel and security tooling
   │  ├─ Management     Log Analytics, automation
   │  ├─ Identity       domain controllers, if you still need them
   │  └─ Connectivity   hub network, firewall, DNS, gateways
   ├─ Landing zones
   │  ├─ Corp           workloads connected to the hub
   │  └─ Online         internet-facing workloads
   ├─ Sandbox           experiments, loose policy, no hub connectivity
   └─ Decommissioned    subscriptions on their way out

Three things worth knowing. First, don't assign anything at the tenant root group. Create an intermediate root with your organization's prefix and put your broad policies there. Second, the Security management group is a fairly recent addition, so older diagrams won't show it. Third, there's also a Local management group for Azure Local clusters; skip it unless you run them.

If one small team runs the whole platform, a single Platform management group with one subscription is fine. Split it only when different teams own networking, identity and security and need different policies.

Roll out policy in Audit before Deny

Deny policies switched on across a busy estate on day one will break deployments and teach teams to resent the platform. I start everything in Audit, watch the compliance data for a few weeks, fix the patterns that fail, then move to Deny one management group at a time.

ScopeWhat I assignEffect
Intermediate rootAllowed regions, required tags, diagnostic settings to the central workspaceDeny / DeployIfNotExists
PlatformMicrosoft Defender for Cloud plans, Azure Monitor Agent with data collection rulesDeployIfNotExists
Landing zonesPrivate endpoints for PaaS, minimum TLS version, no public network access on data servicesDeny
CorpNo public IP addresses, every subnet has an NSG, traffic routed through the hubDeny
SandboxA few region and cost guardrails, nothing moreDeny (limited)

Check which agent your policies deploy. The Log Analytics agent was retired on August 31, 2024, so any policy that still installs it is out of date. Use Azure Monitor Agent with data collection rules.

Keep policy definitions and assignments in Git and deploy them through a pipeline. A policy someone changed in the portal is a policy nobody reviewed.

Use subscriptions as the main boundary

A subscription separates billing, RBAC and policy cleanly. I give each workload its own subscription per environment, plus a separate one for anything with a stricter regulatory scope. Creating them by hand doesn't scale, so build a subscription vending process: a pipeline that creates the subscription, places it in the right management group, applies tags and RBAC, and peers its spoke network to the hub. Every new subscription then starts from a known state instead of a blank one.

Hub and spoke networking

The Connectivity subscription holds the hub virtual network. Mine usually contains:

  • Azure Firewall for egress and east-west inspection. The Premium SKU adds TLS inspection and IDPS if you need them.
  • A VPN or ExpressRoute gateway for on-premises connectivity.
  • Azure Bastion, so nobody needs a public IP on a VM to manage it.
  • DNS Private Resolver and the private DNS zones for private endpoints, kept in one place so every spoke resolves the same names.
  • One DDoS Network Protection plan, shared by every virtual network in the tenant that needs it.

Each workload gets a spoke virtual network peered to the hub, with a route table that sends 0.0.0.0/0 to the firewall. The private DNS zones stay in the hub; spokes don't get their own copies. Once you have hundreds of private endpoints, duplicated zones are an outage waiting to happen.

If you span many regions or have lots of branch connectivity, look at Azure Virtual WAN instead of a hand-built hub. It manages routing between hubs for you, at the cost of some flexibility.

Identity lives mostly in Entra, not Azure Policy

Some identity controls get listed as "landing zone policy" when they aren't. MFA, blocking legacy authentication and sign-in risk are Microsoft Entra Conditional Access settings, not Azure Policy. The landing zone's job is narrower: make privileged Azure access just-in-time with Privileged Identity Management, give workloads managed identities instead of secrets, and review privileged role assignments on a schedule.

Keep the Identity subscription small. It exists for domain controllers that older workloads still depend on. New workloads should use Entra ID directly.

Central logging and security

Every subscription sends logs to a central Log Analytics workspace in the Management subscription, with access split so the security team and the operations team each see what they need. On top of that I add Microsoft Sentinel for detection, Defender for Cloud enabled at management group scope, Azure Update Manager for patching (Automation Update Management was also retired in August 2024), and a budget with alerts on every subscription.

Tags people will actually fill in

Require a short list of tags with policy before workloads land: environment, owner, cost-center, application and data-classification. Five tags filled in correctly beat twenty that everyone ignores. They're what turns one big cloud bill into costs a team can own.

Where to start

  1. Create the management group hierarchy and assign baseline policies in Audit.
  2. Turn on Defender for Cloud and the central Log Analytics workspace.
  3. Build the hub: firewall, Bastion, DNS resolver, private DNS zones and on-premises connectivity.
  4. Vend the first workload subscription and peer its spoke.
  5. Move policies from Audit to Deny as teams adjust.

You don't have to write all of this yourself. Microsoft publishes landing zone accelerators in Bicep and Terraform. The real work is deciding which policies to enforce and how your network should look, and that part is worth doing slowly.
