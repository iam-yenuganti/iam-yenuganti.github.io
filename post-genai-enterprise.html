Running Generative AI in Production on Azure: The Platform Under the Chat App

⏱ 8 min read 📅 February 12, 2026 ✍️ Srinivas Yenuganti
Generative AI RAG Azure AI Search API Management Microsoft Foundry

A generative AI prototype takes a week. What comes after is mostly the same on every project, and very little of it is about the model. This is the platform I put under a chat or question-answering app before real users touch it.

It's written for the common case: people asking questions that should be answered from the organization's own documents. Agents that take actions are a different problem, and I cover them in a separate post on agents and MCP.

Pick the pattern from the question

Most enterprise requests turn out to be "answer from our documents," which means retrieval-augmented generation (RAG): fetch the relevant passages, give them to the model and ask it to answer only from them. Fine-tuning is useful when you need a particular format or style the model won't produce from instructions, but it's rarely where I start. It doesn't teach the model your latest policy document, and every model upgrade means doing it again.

Retrieval decides the quality

When answers are wrong, the cause is usually retrieval, not the model. Fix retrieval before you pay for a bigger model.

  • Use hybrid search. Azure AI Search runs keyword and vector queries in parallel and merges them with Reciprocal Rank Fusion. Keywords catch exact terms like product codes and names. Vectors catch meaning. Add the semantic ranker on top to re-score the merged results.
  • Chunk with structure in mind. The built-in indexer and skillset can split and embed content for you. For PDFs with tables and headings, extract structure first with Document Intelligence so a chunk doesn't start in the middle of a table.
  • Keep metadata on every chunk. Document name, section, date and classification. You need them for filtering and for citations.
  • Trim results to the user. Retrieval must return only what the person asking is allowed to see. If it doesn't, the model will happily summarize a document the user could never open.

For complex questions, Azure AI Search also offers agentic retrieval, where a model plans several sub-queries across knowledge sources. Query planning is still in preview, so I use it where classic hybrid search falls short, not by default.

Put an AI gateway in front of the models

I don't let applications call model deployments directly. They call API Management, which gives me one place for the controls that every app needs:

  • Token limits per app. The llm-token-limit policy sets tokens per minute or a quota per subscription key, so one team's batch job can't starve everyone else.
  • Usage metrics. The token metric policy sends usage to Application Insights, which is how you do chargeback.
  • Load balancing and failover. Deploy models in two regions and let the gateway spread traffic and retry.
  • Semantic caching. With Azure Managed Redis, similar prompts can reuse a previous answer. I only turn this on for FAQ-style apps where a slightly stale answer is acceptable.
  • Content safety checks. A policy can send prompts to Azure AI Content Safety before they reach the model.
<llm-token-limit counter-key="@(context.Subscription.Id)"
    tokens-per-minute="500" estimate-prompt-tokens="false"
    remaining-tokens-variable-name="remainingTokens" />

The backend call from API Management to Foundry uses a managed identity, so there are no API keys in the app or the gateway.

Keep it private

Foundry, AI Search and the storage behind ingestion all get private endpoints, with public network access turned off. Services authenticate to each other with managed identities. The result is that prompts, retrieved documents and answers never cross the public internet, and there's no key to leak.

Guardrails that match the risk

Foundry guardrails filter harmful content in prompts and responses, and Prompt Shields detect attacks. Two details matter for RAG:

  • User prompt attack detection is on by default. Document attack detection, which catches instructions hidden in retrieved content, is off by default. For RAG you want it on.
  • The safety system can only tell documents from user input if you mark them. Wrap retrieved content in the documented <documents> delimiter inside the message so indirect attack and groundedness checks know what's what.

Guardrails reduce risk. They don't prove an answer is right, which is what evaluations are for.

Evaluate like you test code

Prompts, chunking, index settings and model versions all change answer quality in ways unit tests can't see. I treat evaluation as part of CI:

  1. Keep a golden set of real questions with expected answers, written by people who know the domain, not generated by the model.
  2. Run evaluations for groundedness and relevance on every change to prompts, the index or the model deployment.
  3. Block the release if quality drops against the last accepted baseline.
  4. Have a person read a sample of answers each week. Scores miss things people notice.

Watch the cost per answer

  • Right-size the model. Model router in Foundry picks a model per prompt, with Balanced, Cost or Quality modes. When a workflow needs the same model every time, pin a deployment instead.
  • Use prompt caching. Keep the long, reused part of the prompt (instructions, examples) identical and at the start. On newer model families, cache writes can be billed as well as discounted reads, so a stable prefix matters more than it used to.
  • Consider provisioned throughput for steady, predictable traffic, and size it with the capacity calculator rather than guessing.
  • Track cost per answer, not just the monthly total. If it creeps up, something is sending more context or more calls than it should.

What I build first

  1. Private networking and managed identities.
  2. API Management in front of the models, with token limits and usage metrics.
  3. An AI Search index with hybrid search, semantic ranking and security trimming.
  4. Guardrails with document attack detection on.
  5. A golden question set and an evaluation step in the pipeline.

Then the chat app. Done in that order, the app is the small part.
