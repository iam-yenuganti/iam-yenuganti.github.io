Passwordless Azure Deployments from GitHub Actions: A Secure Architecture

12 min read · 22 September 2026

Scenario

Application teams deploy Terraform and application releases into separate Azure development subscriptions. Currently, pipelines rely on long-lived client secrets shared across repositories, creating significant security risk and maintenance overhead. The platform team must migrate each repository to GitHub OpenID Connect (OIDC), scope federated identities and Azure Role-Based Access Control (RBAC) by environment, require protected-environment approval for production, and retain evidence tying a workflow run to an Azure deployment.

Target Architecture

The target architecture eliminates static credentials by establishing a trust relationship between GitHub Actions and Microsoft Entra ID. Instead of storing secrets, the workflow requests a short-lived token from GitHub, which is exchanged for an Azure access token via Microsoft Entra Workload Identity Federation.

Key components include:

  • Identity Provider: GitHub Actions issues OIDC tokens.
  • Trust Anchor: Microsoft Entra application or user-assigned managed identity configured with a federated identity credential.
  • Access Control: Azure RBAC assigned to the identity, scoped narrowly to specific resource groups or subscriptions.
  • Workflow Protection: GitHub Environments with required reviewers for high-risk stages.

This design ensures that no long-lived secrets exist in the repository. Access is granted only when a workflow runs, and only if the token claims match the federated credential configuration.

Request and Approval Flow

The deployment flow follows a strict sequence to ensure security and auditability:

  1. Engineer starts workflow: A push or pull request triggers the GitHub Actions workflow.
  2. GitHub environment approval: For protected environments (e.g., Production), the job pauses until a designated reviewer approves the deployment.
  3. OIDC token issued: GitHub issues a short-lived OIDC token containing claims about the repository, branch, and environment.
  4. Microsoft Entra validates federation: The Azure Login action sends the token to Microsoft Entra ID. Entra validates the token against the federated identity credential (checking issuer, subject, and audience).
  5. Scoped Azure role activated: Upon validation, Microsoft Entra issues an access token. Azure RBAC evaluates the token against the assigned roles (e.g., Contributor on a specific Resource Group).
  6. Deployment and audit evidence: The deployment executes. Audit logs record the identity used and the actions performed.

Implementation Steps

Migration requires configuring both the identity trust and the workflow permissions.

1. Configure Federated Identity Credential

Create a Microsoft Entra application or user-assigned managed identity. Configure a federated identity credential to trust tokens from GitHub Actions. The credential must specify the GitHub repository, branch, and optionally the environment. The issuer, subject, and audience values must case-sensitively match the token claims.

For public clouds, the default audience is api://AzureADTokenExchange. For non-public clouds, update this parameter accordingly.

2. Set Up GitHub Secrets

Store the AZURE_CLIENT_ID, AZURE_TENANT_ID, and AZURE_SUBSCRIPTION_ID as GitHub secrets. For enhanced security in public repositories, use environment secrets instead of repository secrets. If the environment requires approval, the job cannot access these secrets until a reviewer approves it.

3. Update Workflow Permissions

Modify the GitHub Actions workflow to request an OIDC token. Add permissions: id-token: write to the job. This is required to fetch the OIDC token.

jobs:
  deploy:
    permissions:
      id-token: write
    runs-on: ubuntu-latest
    steps:
      - name: Azure Login
        uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

4. Scope RBAC by Environment

Assign Azure RBAC roles to the identity. Follow least-privilege principles. Avoid broad roles like Owner. Use narrower built-in roles or custom roles scoped to specific resource groups.

Environment RBAC Scope Role Assignment Approval Required
Development Resource Group: Dev Contributor No
Test Resource Group: Test Contributor No
Staging Resource Group: Staging Contributor Yes (Reviewer)
Production Resource Group: Prod Contributor Yes (Reviewer + PIM)

Audit and Evidence

It is critical to distinguish between access-governance records and resource-operation logs. Microsoft Entra ID logs the authentication and token issuance events. Azure Activity Logs record the resource operations performed by the identity. The workflow run ID and the Azure deployment ID should be correlated in your CI/CD dashboard to provide end-to-end traceability.

Do not assume that the access system records changes performed in the resource plane. Azure RBAC controls access, but Azure Monitor and Activity Logs provide the evidence of what was changed.

Failure Modes and Trade-offs

Token Validation Failures: If the issuer, subject, or audience in the federated credential does not match the token claims, authentication fails. This is a common misconfiguration during migration.

Secret Exposure: While OIDC eliminates client secrets, the Client ID and Subscription ID are still stored as GitHub secrets. These are not secrets in the cryptographic sense but should be protected. Using environment secrets adds an additional layer of protection.

Complexity: Managing federated credentials for multiple repositories and environments can be complex. Automation via Terraform or Bicep is recommended to manage these configurations at scale.

Privileged Access: For production, consider using Microsoft Entra Privileged Identity Management (PIM) to provide just-in-time access. This lowers the exposure time of privileges and increases visibility.

Implementation Checklist

  • [ ] Create Microsoft Entra application or user-assigned managed identity.
  • [ ] Configure federated identity credential with correct issuer, subject, and audience.
  • [ ] Assign least-privilege Azure RBAC roles to the identity.
  • [ ] Store Client ID, Tenant ID, and Subscription ID as GitHub secrets.
  • [ ] Update GitHub Actions workflow to use id-token: write permission.
  • [ ] Configure GitHub Environments for staging and production with required reviewers.
  • [ ] Validate that audit logs capture both authentication and resource operations.
  • [ ] Remove old client secrets from repositories and rotate any compromised credentials.

Conclusion

Migrating to passwordless deployments using GitHub OIDC federation significantly reduces the attack surface by eliminating long-lived secrets. By combining federated identities with least-privilege RBAC and environment protections, organizations can achieve a secure, auditable, and maintainable deployment pipeline. This architecture aligns with modern security best practices and reduces the operational burden of secret rotation.
