An Azure Monitoring Baseline That Actually Helps

5 min read · 24 September 2026

I've seen plenty of Azure subscriptions with thousands of metrics and gigabytes of logs where the on-call engineer still couldn't answer the first question in an incident: which customer-facing service is broken? More telemetry didn't help. What helps is a small, deliberate baseline: which signals you collect, where they go, who can read them, and which changes wake someone up.

This post is the baseline I put in place on a new platform before anyone asks for dashboards.

Know what Azure gives you for free

Three kinds of platform data matter here, and they don't behave the same way:

  • Platform metrics are collected automatically. You can chart and alert on them without any setup.
  • The activity log is also automatic. It records control-plane changes: who created, changed or deleted what.
  • Resource logs are not collected at all until you create a diagnostic setting on each resource. These are the logs that explain what actually happened inside a Key Vault, an App Service or a database.

That last point catches teams out constantly. The workspace exists, metrics show up in the portal, everyone assumes logging is "on", and then the first real incident reveals that nobody ever configured Key Vault audit logs.

One naming trap too: a Log Analytics workspace stores logs and traces you query with KQL. An Azure Monitor workspace stores Prometheus metrics you query with PromQL. They're different things, and this post is about the first one.

Start with one workspace

Microsoft's own design guidance says to start with a single Log Analytics workspace and add more only when a specific requirement forces it. Data volume isn't one of those reasons, because the amount of data in a workspace doesn't create performance limits. One workspace means one place to query during an incident, and it can make you eligible for a commitment tier discount.

Good reasons to split are concrete ones:

  • Data has to stay in a particular region.
  • You have multiple Microsoft Entra tenants.
  • Different owners must not see each other's data, and table-level or resource-context access isn't enough.
  • The same table needs different retention for different resources.
  • The security team wants Microsoft Sentinel in its own workspace.

Write down the reason for every extra workspace. Each one makes incident queries harder, so it should be a decision, not an accident.

Collect logs by question, not by checkbox

Turning on every log category for every resource feels safe and gets expensive fast. Diagnostic settings don't let you filter within a category, so whatever you select, you pay to ingest. I start from the questions an engineer will ask during a failure: did requests fail, what changed, and which component was involved? Then I pick the categories that answer them.

Category groups help. Where a service supports them, audit collects the logs that record access to data and changes to settings, and allLogs collects everything. For most security-relevant resources, audit is a sensible default:

param workspaceId string
param keyVaultName string

resource kv 'Microsoft.KeyVault/vaults@2023-07-01' existing = {
  name: keyVaultName
}

resource diag 'Microsoft.Insights/diagnosticSettings@2021-05-01-preview' = {
  name: 'to-law'
  scope: kv
  properties: {
    workspaceId: workspaceId
    logs: [
      {
        categoryGroup: 'audit'
        enabled: true
      }
    ]
  }
}

Notice there's no AllMetrics block. Platform metrics are already available in metrics explorer and metric alerts. Only send them to the workspace if you really need them in KQL, because otherwise you're paying twice for the same data.

At scale, don't rely on every team remembering this. Azure Policy has built-in DeployIfNotExists policies that create diagnostic settings using category groups, so new resources get logging automatically.

The small print that bites later

  • The destination must exist before you create the setting.
  • For regional resources, a storage account or event hub destination must be in the same region as the resource. A Log Analytics workspace doesn't have that restriction.
  • A resource can have at most five diagnostic settings.
  • Data can take up to about 90 minutes to start flowing after you create a setting, so an empty query right after deployment isn't proof of failure.
  • When you delete, rename or move a resource, delete its diagnostic settings too. Otherwise a new resource with the same name can quietly inherit the old setting.

I add that last one to every decommissioning checklist, because nobody remembers it otherwise.

Alerts should describe pain, not metrics

A CPU-above-80% alert across the whole platform generates noise and rarely tells anyone a customer is affected. For each critical service, I'd rather have two or three alerts on symptoms users would notice, such as failed requests or slow responses on the main journey, each with an owner and a runbook.

A good test: from the notification alone, can the responder tell which service is affected, since when, and where to look first? If not, the alert needs work, not more alerts beside it.

Check the baseline itself

Monitoring can fail silently, so I measure it like anything else:

  • What share of in-scope resources have the intended diagnostic settings?
  • When did each important resource last send a log?
  • Did the last test alert actually reach a person?

After each incident, ask which alerts helped, which were noise, and what you had to find by hand. That review improves the baseline more than any template.

Where to start

  1. Pick one important production service and write down its owner, its main user journey and the questions you'd ask if it broke.
  2. Create or confirm a single workspace, and document any reason you need more.
  3. Add diagnostic settings for the resources on that journey, using the audit group or the specific categories you need, and confirm data arrives.
  4. Add two or three symptom alerts with an owner and a runbook, and fire a test.
  5. Turn what worked into a policy and a template for the next team.

The goal isn't maximum telemetry. It's being able to spot a real problem, reach the right person, and hand them the evidence.
