Ransomware-Resilient Backups on Azure

6 min read · 28 September 2026

A green "backup succeeded" tile tells you very little about whether you'd survive ransomware. Attackers who get admin rights know where the backups are. They stop protection, shorten retention, delete recovery points, or simply wait until encrypted data has rolled into every copy you keep.

So I design backup protection around one question: if someone holds a fully privileged account in this subscription, can they still destroy my ability to recover? Azure Backup gives you the pieces to answer "no", but only if you put them together deliberately. This post covers vaulted backups in Recovery Services vaults and Backup vaults, not snapshots or operational backups, which behave differently.

Start with what each system can lose

Before touching a vault policy, write down three numbers for each application: how much data it can afford to lose, how long a restore can take, and how far back you need clean history. That last one gets skipped. If it takes you three weeks to notice an intrusion, a two-week retention window means every recovery point you have may already be compromised.

Frequent backups and long retention solve different problems. Frequent backups limit data loss. Long retention outlasts slow detection. Neither helps if an attacker can delete the copies, which is what the next three controls are for.

Soft delete: your safety net, now always on

Soft delete keeps deleted backup data recoverable for a retention window. The default is 14 days, you can extend it to 180, and the first 14 days cost nothing extra. Beyond that you pay normal backup rates for the extra days.

The good news is that Microsoft now enforces soft delete by default. For Recovery Services vaults it's generally available, and you can't switch it off through the portal, CLI, PowerShell or API. For Backup vaults it's generally available in a few regions and in preview in the rest, where it can still be disabled in the portal. Check which one you have rather than assuming.

Two limits matter. Soft delete doesn't cover operational backups of blobs or Azure Files shares. And while it does apply to VM instant-restore snapshots and operational disk backups, those can still be accessed and deleted directly before the window ends. That's why I treat the vaulted copy as the one that counts.

My advice: raise the window above 14 days for anything important. The extra storage cost is small next to discovering an attack on day 20.

Immutability: test it, then lock it

An immutable vault blocks operations that would lose recovery points: deleting data when you stop protection, and reducing retention in a policy. It has three states:

  • Disabled: nothing is blocked.
  • Enabled: destructive operations are blocked, but anyone with enough rights can turn it off again.
  • Enabled and locked: the setting can never be reversed, and backups move to WORM storage.

Only the locked state actually protects you from a compromised admin. "Enabled" is useful for testing, but an attacker can simply disable it first. If an audit asks whether your vault is immutable, the honest answer depends on whether it's locked.

You also choose how long recovery points stay immutable. The default ties immutability to the policy's retention. The alternative is a fixed number of days, after which recovery points still exist under normal retention but can be deleted. A fixed duration keeps storage costs down, but be clear that a 180-day policy with 30 days of immutability only gives you 30 days of real protection.

Because locking is irreversible, I always try it on a pilot vault first: change policies, decommission a test VM, and make sure the restrictions don't break any routine operation. Then I lock.

Resource Guard: a second person for critical changes

Immutability stops data from being destroyed. Multi-user authorization (MUA) stops someone from quietly weakening the vault in the first place. It works through a separate Azure resource called Resource Guard. Critical operations on the vault, such as disabling protection features or changing policies, only succeed if the person also has rights on the Resource Guard.

The whole point is separation, so placement matters:

  • Same subscription as the vault: the weakest option.
  • Different subscription, same tenant: better.
  • Different tenant: the strongest, because credentials stolen in your main tenant can't approve anything.

The Resource Guard has to be in the same region as the vault. Most importantly, backup admins must not hold Contributor, Backup MUA Admin or Backup MUA Operator on the Resource Guard. If they do, MUA protects nothing. Microsoft's own guidance pairs this with Privileged Identity Management so approvers get just-in-time access rather than standing rights.

Watch for what's missing, not just what failed

Built-in Backup alerts and Backup Reports will tell you about failed jobs. The more dangerous signal is silence: a VM that was never added to a policy, or protection that was stopped last Tuesday. I run a regular coverage check against the application inventory and alert on stopped protection, policy changes and soft-deleted items, all routed to someone who will actually act.

Track two dates per application: the last successful backup and the last successful tested restore. They tell you different things.

Practise the restore, not just the button

A restore drill should start from a scenario, like "this database was encrypted three days ago." Pick a recovery point from before that, restore into an isolated environment, and check the application actually works: data consistent, users can sign in, dependencies connect. Restored systems shouldn't touch production until they pass.

Time the whole thing, from declaring the incident to a working service, and compare it with the objectives you wrote down at the start. Include the awkward parts: getting Resource Guard approval out of hours, recovering secrets and keys, and rebuilding network access. The first drill usually finds a dependency nobody documented. Better then than during a real attack.

Where to start

  1. List which workloads have vaulted backups and which only have snapshots or operational copies.
  2. Raise soft-delete retention to cover your realistic detection time.
  3. Enable immutability on a pilot vault, test your routine changes, then lock it.
  4. Put a Resource Guard in a separate subscription or tenant, and check nobody on the backup team has rights on it.
  5. Run a restore drill for one important application and fix what it finds.

None of these controls is ransomware-proof on its own. Together, owned by different people, they make it very hard for one compromised account to take away your way back.
