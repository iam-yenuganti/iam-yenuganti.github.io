Locking Down Azure Key Vault

7 min read · 27 September 2026

Key Vault is the one Azure resource where a small mistake has a long tail. If someone reads a secret they shouldn't, you rotate it. If someone deletes the key that encrypts a storage account, you may not get your data back. So I treat every vault as its own security boundary, not a shared bucket that every team writes into.

This is the setup I use: small vaults, no public network path, Azure RBAC for everything, managed identities for every workload, and deletion that can be undone.

One vault per application, per environment

A vault shared by ten applications means ten teams with a reason to need access, and one compromised identity that can read all of their secrets. I give each application its own vault in each environment: kv-billing-dev, kv-billing-prod, and so on. Vaults are free to create and you pay for operations, so there's no cost reason to share.

It also makes access reviews readable. "Who can read secrets in kv-billing-prod?" has a short answer.

Use Azure RBAC, not access policies

Key Vault has two permission models. Access policies are the older one. Azure RBAC is the one Microsoft recommends, and since API version 2026-02-01 it's the default for newly created vaults.

The reason I care is who can hand out access. With RBAC, granting someone access to keys, secrets or certificates requires Owner or User Access Administrator. RBAC also works with Privileged Identity Management, so admin access can be time-limited and expire on its own, and you can use deny assignments when you need to carve something out.

The roles I use most:

  • Key Vault Secrets User for applications that only read secrets.
  • Key Vault Crypto Service Encryption User for services that use a customer-managed key, like Storage or SQL.
  • Key Vault Secrets Officer or Key Vault Administrator for people, only through PIM.

Watch one thing: Key Vault Contributor manages the vault itself, not its contents. It doesn't let you read a secret. People are often surprised by that the first time they switch to RBAC.

Two practical notes. Existing vaults keep whatever model they have; updating your templates to the new API version doesn't migrate anything. And all Key Vault control-plane API versions before 2026-02-01 retire on February 27, 2027, so update your Bicep, Terraform providers, CLI and SDKs before then.

No public network path

I set publicNetworkAccess to Disabled and connect through a private endpoint, with the privatelink.vaultcore.azure.net zone linked to the networks that need it. Workloads reach the vault on a private IP, and nothing on the internet can talk to the data plane.

I avoid IP allow-lists as the main control. They drift, they're hard to review, and they still leave the vault reachable from the internet for anyone on an allowed address. If a Microsoft service genuinely needs to reach the vault, check whether it's on the trusted services list before opening anything else.

The usual way this goes wrong is DNS, not security. If an application resolves the public name instead of the private one, it fails to connect. When a new workload can't reach its vault, check name resolution first.

Managed identities only

Applications get a managed identity and a role assignment on their own vault. No client secrets, no connection strings in app settings, nothing in a repository. The irony of storing a credential to read your credential store is worth avoiding.

Make deletion recoverable

Soft delete is on by default for new vaults and can't be turned off. Deleted vaults and objects stay recoverable for a retention period between 7 and 90 days, 90 by default. You choose that number when you create the vault and can't change it later.

Purge protection is the part people skip, and it's off by default. Without it, someone with enough rights can delete a vault and then purge it immediately. With it, nobody can purge a deleted vault or object until the retention period ends. Not an administrator, and not Microsoft. Recovery still works the whole time; purge protection only stops permanent deletion.

Turn it on for every vault that holds encryption keys. Most Azure services that use customer-managed keys require it anyway. The trade-off is that a deleted vault's name stays reserved until the retention period ends, which matters if your naming scheme assumes you can recreate a vault straight away.

Admin access through PIM

Nobody has standing admin rights on a production vault. Engineers are eligible for Key Vault Administrator or Secrets Officer, activate it in PIM with MFA and a reason, and lose it after a few hours. In production I add an approval step.

Development vaults can be looser. Developers often need to read and set secrets there all day, and making them request access every morning just teaches people to work around the process.

Logs worth keeping

Two sources answer most questions:

  • Key Vault diagnostic logs (the AuditEvent category), sent to Log Analytics. They show every data-plane operation: who read which secret, and when.
  • Azure Activity Log for control-plane changes: network settings, role assignments, deletes.

PIM's own audit history tells you who was allowed to act and why. The vault logs tell you what they actually did. You want both when someone asks about an incident.

I alert on a few things: a secret read by an identity that has never read it before, any change to network settings on a production vault, and any delete.

Enforce it with Azure Policy

None of this holds unless something checks it. Built-in Azure Policy definitions cover most of it: vaults should use private link, should have purge protection enabled, should use the RBAC permission model, and should have public network access disabled. I start them in audit mode, fix what they find, then switch the important ones to deny.

Where to start

  1. List your vaults and note which still use access policies or allow public access.
  2. Turn on purge protection for any vault holding keys used for encryption.
  3. Migrate one vault to RBAC, update the applications to use managed identities, then do the rest.
  4. Add private endpoints, production first, and test DNS from every network that needs access.
  5. Move admin access into PIM and remove standing assignments.
  6. Update your templates and tools to Key Vault API version 2026-02-01 or later before the February 2027 retirement.
