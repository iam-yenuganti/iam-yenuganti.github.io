Building AI Agents with MCP on Azure Without Losing Control

⏱ 8 min read 📅 March 18, 2026 ✍️ Srinivas Yenuganti
AI Agents MCP Microsoft Foundry Agent Framework API Management

Most agent demos I see have the same shape: a model, a long system prompt, and a bag of tools that can do almost anything. It works on stage. The first time someone asks to put one into production, the questions are about the tools, not the model. What can this thing change? Who approved it? Where's the log?

This post is how I answer those questions on Azure. It centers on the Model Context Protocol (MCP), which has become the usual way to hand tools to an agent, and on the controls I put around it.

MCP in one paragraph

MCP is an open protocol for connecting models to tools and data. An MCP server exposes capabilities, and an MCP client inside the agent host calls them. A server can offer tools the model can call, resources it can read, and reusable prompts. Remote servers talk over Streamable HTTP, which replaced the older HTTP plus server-sent events transport. The appeal is reuse: a tool written once works with any MCP client, whether that's GitHub Copilot in VS Code, a Foundry agent or something you wrote yourself.

That reuse is also the risk. An MCP server is an API that a model decides when to call. It deserves at least the care you give any other API, and probably more, because this caller can be talked into things.

The pieces I use on Azure

  • Agent runtime. Foundry Agent Service when I want Microsoft to host the agent loop and conversation state. Microsoft Agent Framework when I want the loop in my own code, usually on Container Apps. Agent Framework is the successor to both Semantic Kernel and AutoGen, built by the same teams, so new work starts there.
  • Models. Deployed in Microsoft Foundry and reached through a private endpoint.
  • Tools. MCP servers on Azure Functions or Container Apps, published through API Management.
  • Knowledge and state. Azure AI Search for retrieval, Cosmos DB for task state.
  • Tracing. Application Insights, with one trace per agent run.

Split tools by what they can change

The most useful single decision is to separate read tools from write tools and put them in different MCP servers with different identities.

The read server gets read-only access: query metrics, search logs, look up a ticket. The write server gets the narrow rights it needs for one job, such as restarting an app, and nothing more. If someone steers the agent with a poisoned document, the worst it can do through the read server is read. One big server with every tool and a Contributor identity throws that boundary away.

Foundry Agent Service makes the next step easy. When you attach an MCP server to an agent, allowed_tools limits which of its tools the agent can see, and require_approval decides which calls need a human. Approval defaults to always. I keep that default for the write server and relax it only for read tools I've watched for a while. The tool definition looks roughly like this:

{
  "type": "mcp",
  "server_label": "ops_read",
  "server_url": "https://apim-contoso.azure-api.net/ops-read-mcp/mcp",
  "allowed_tools": ["query_metrics", "search_logs"],
  "require_approval": "never"
}

Put API Management in front of every MCP server

API Management can expose an existing MCP server, or turn a REST API it already manages into an MCP server where each operation becomes a tool. Either way I get the controls I already use for APIs:

  • Validate an Entra ID token on every call, so only the agent's identity reaches the tools.
  • Rate limit per tool and per caller. An agent stuck in a loop hits the limit, not your backend.
  • Log every call with a correlation ID that matches the agent's trace.

Two details from the docs worth knowing. In MCP server policies, don't read the response body, because that forces buffering and breaks the streaming MCP relies on. And when you expose a REST API as an MCP server, API Management supports tools but not MCP resources or prompts.

Treat tool descriptions and tool output as untrusted

Prompt injection against agents rarely arrives through the chat box. It arrives in what the agent reads: a web page, an email, a ticket comment, even a tool's own description. Microsoft's Foundry guidance says to treat provider-supplied tool descriptions as untrusted and to enforce permissions and approvals independently of what the model decides. I agree, and I add a few habits:

  • Connect only to MCP servers that you or a trusted provider host, not a proxy someone found online.
  • Review tool descriptions when a server changes, the way you'd review a dependency upgrade.
  • Turn on Prompt Shields for document attacks. In Foundry it can also scan tool responses for supported tools (in preview). Document attack detection is off by default, so check.
  • Validate tool inputs on the server: types, lengths, allowed values. Never pass model output straight into a shell command or a SQL string.

Put limits on the loop

Agents call tools in a loop until they decide they're done. That loop needs limits you set, not limits the model sets: a maximum number of tool calls per run, a token budget per session and a timeout. When a run hits a limit, stop it and alert someone. On the model side, the llm-token-limit policy in API Management caps tokens per caller, so one runaway agent can't eat the shared quota.

One trace per run

When something goes wrong, the question is always "why did it do that?" You can only answer it if every model call and tool call from a run lands in one trace. I tag traces with the agent name, run ID and user, and I alert on three things: loop depth, tool error rate and tokens per run. A sudden jump in any of them usually means a bug, a model change or someone poking at the agent.

Where I start

  1. One agent, one job, read-only tools.
  2. MCP servers behind API Management with Entra auth and rate limits from day one.
  3. Write tools in a separate server with its own identity, with approval required.
  4. Tracing and alerts in place before the first real user.
  5. Loosen approval for specific tools only after you've watched what the agent does with them.

None of this is new. It's least privilege, an API gateway and good logs, applied to a caller that can be persuaded. That last part is the only genuinely new risk, and it's the reason the boundaries have to live outside the model.
