Setting Up an AI Coding Assistant for Infrastructure Work

⏳ 7 min read 📅 April 28, 2026 🔧 Hands-on: VS Code, GitHub Copilot, Azure MCP Server ✎️ Srinivas Yenuganti
GitHub Copilot VS Code Azure MCP Server Terraform Infrastructure as Code

AI coding assistants are most useful to infrastructure engineers when they live where the code is: in the editor, next to the Terraform, with access to the terminal and to Azure. They're also most dangerous there, for exactly the same reason. An assistant that can run commands can run the wrong one.

This is how I set up GitHub Copilot in VS Code for Terraform, Bicep and Azure work, and the habits that keep it from doing something I'll regret. Most of it carries over to other editors and assistants. The details of each tool change every few months, so I've stuck to the parts that don't.

Use agent mode, and know what it can do

Copilot Chat has a plain chat mode and an agent mode. In agent mode it can read and edit files across the workspace, run terminal commands and call tools from MCP servers, then iterate on the result. That's what makes it useful for "add diagnostic settings to every resource in this module." It's also why every tool call it makes should be something you understand and allowed on purpose.

Write a repository instructions file first

Copilot reads .github/copilot-instructions.md from the repository and adds it to every request in that workspace. This is the highest-value ten minutes of the whole setup. Without it, the assistant writes generic code. With it, it writes your code.

# Platform infrastructure: instructions for AI assistants

## What this repo is
Terraform for the shared Azure platform: hub network, private DNS,
monitoring, and per-application landing zones.

## Conventions
- Terraform with the azurerm provider; use the versions pinned in versions.tf
- Names: {app}-{env}-{region}-{type}, for example payments-prod-eus2-kv
- Tags on every resource: environment, owner, cost-center
- Modules live in modules/, one module per folder, with a README

## Non-negotiables
- No secrets in code, variables files or examples. Use Key Vault references.
- public_network_access_enabled = false unless the README says otherwise
- Managed identities only; no client secrets for service-to-service auth
- Role assignments at resource-group scope or narrower, never subscription

## Before proposing a change
- Run terraform fmt and terraform validate
- Show the expected terraform plan summary, and call out anything destroyed

Treat this file like code: review changes to it in pull requests. It shapes everything the assistant writes for your team.

Give it Azure context with the Azure MCP Server

The Azure MCP Server lets the assistant look things up in your Azure environment: list resource groups, read a resource's configuration, query logs. Install it as a VS Code extension (it also comes with GitHub Copilot for Azure), or add it to the workspace in .vscode/mcp.json:

{
  "servers": {
    "Azure MCP Server": {
      "command": "npx",
      "args": ["-y", "@azure/mcp@latest", "server", "start"]
    }
  }
}

It signs in with your Entra ID identity, and if you're already signed in with the Azure CLI it uses that. Two consequences follow:

  • The assistant has your permissions. If your account can delete a production resource group, so can a tool call you approve without reading. I use an account with Reader on production for day-to-day work and elevate separately when I actually need to change something.
  • Approvals matter. When the agent wants to run a tool, VS Code asks, and you can allow it for the current session, the workspace or always. I allow read operations for the session. I never choose "always allow" for anything that writes.

How I make a Terraform change with it

  1. Describe the change and the constraints. Point at the module and the instructions file rather than pasting everything.
  2. Let the agent edit the files, then read the diff. All of it.
  3. Run terraform fmt, terraform validate and terraform plan myself, or let the agent run them and read the output myself.
  4. Open a pull request. CI runs the same checks plus static analysis, and a colleague reviews it.
  5. The pipeline applies it. Not the agent, and not me from a laptop.

The rule that holds all of this together: the agent never runs terraform apply against a shared environment.

Prompts that work for infrastructure

Specific beats clever. Three I use often:

  • Reviewing a plan. "Here's a terraform plan. List every resource that will be destroyed or replaced, explain why for each, and tell me which attribute change forces it."
  • Writing a module. "Write a module for a Key Vault with RBAC authorization, purge protection, a private endpoint in the subnet passed as a variable, and diagnostic settings to the Log Analytics workspace passed as a variable. Follow the repo instructions. Don't add anything I didn't ask for."
  • Explaining a failed run. "This pipeline failed. Here's the log. Tell me the most likely cause, what evidence in the log supports it, and what you'd check next. Don't change any files yet."

The "don't change any files yet" line is doing real work. Diagnosis and changes are separate steps.

Mistakes I watch for

  • Invented arguments. Plausible attribute names that the provider doesn't have, or had two major versions ago. terraform validate catches most of these.
  • Defaults that open things up. Public network access left on, firewall rules for 0.0.0.0/0, storage with shared key access enabled.
  • Over-broad roles. Contributor or Owner at subscription scope "to make it work."
  • Old names. Services get renamed often. If the assistant talks about Azure AD or Azure AI Studio, its knowledge of that area is out of date, so check the current docs.
  • Packages that don't exist. Before installing a module or package it suggests, confirm it's real and maintained.

For a team

  • Put the instructions file in every infrastructure repository and review it like code.
  • Agree on what can go in a prompt. No secrets, no customer data, no production connection strings. That's policy, not preference.
  • Keep humans as required reviewers on infrastructure pull requests. AI review can add to that, but it doesn't replace it.
  • Share prompts that work. A short list in the repo wiki beats everyone rediscovering them.

A first week

  1. Day 1: write the instructions file for one repository.
  2. Day 2: add the Azure MCP Server and use it only for read-only questions.
  3. Day 3: have the agent explain the last three failed pipeline runs.
  4. Day 4: make one small module change end to end through a pull request.
  5. Day 5: write down what it got wrong, and add the lessons to the instructions file.

Day 5 is the one people skip, and it's the one that makes the next week better.
