AI Agents in DevOps: Where I Let Them Act and Where I Don't

⏱ 8 min read 📅 May 10, 2026 ✍️ Srinivas Yenuganti
DevOps Azure SRE Agent Azure Copilot AI Agents Platform Engineering

A deployment fails at 2 a.m. Whoever is on call opens a laptop, digs through logs, traces the failure back through three pipeline stages, and finally finds that someone renamed a GitHub environment, so the federated credential no longer matches. Forty minutes for a one-line fix.

An agent can do most of that digging before the on-call engineer has found their glasses. That's real now, not a pitch. It's also why people keep asking whether DevOps is over. My answer is no, but the part of the job that's mostly reading logs is shrinking fast. What's left is deciding what the agents may touch, and checking their work.

What's actually available on Azure

  • Azure Copilot in the portal answers questions about your environment and now includes agents for troubleshooting, observability, deployment, optimization, resiliency and migration. Some are generally available and some are in preview. It acts with your own permissions and asks you to confirm before it changes anything.
  • Azure SRE Agent connects to your Azure resources, monitoring, incident platform (Azure Monitor alerts, PagerDuty or ServiceNow) and source repositories. When an alert fires, it investigates, correlates with recent deployments, proposes a mitigation and, depending on how you configure it, carries it out.
  • Coding agents in GitHub and in the IDE can take an issue or a failing run, work on a branch and open a pull request for review.

Run modes are the setting that matters

SRE Agent has two run modes. In Review mode it proposes an action and an SRE Agent administrator approves or denies it. In Autonomous mode it acts and reports what it did. You set the mode per incident response plan and per scheduled task.

Here's the detail that's easy to miss: the agent-level default is Review, but new incident response plans and scheduled tasks default to Autonomous. Check every plan you create. Microsoft's own recommendation matches mine: production incidents and security alerts in Review, nonproduction and routine reports in Autonomous, and only move a production trigger to Autonomous after you've approved the same fix for it repeatedly over a few weeks.

Two more things to know about Review mode. The approve and deny buttons apply to Azure infrastructure operations. Other actions, like posting to Teams or sending email, proceed based on your instructions, so use hooks or tool access policies if those need governing too. And some guardrails are built in: the agent won't run delete commands, blocks Key Vault commands, and respects resource locks.

The identity is the real limit

Whatever the agent decides, it can only do what its managed identity is allowed to do. If you give it Contributor on a subscription, that's its blast radius. I scope the identity to the resource groups it looks after, use separate agents or identities for production and nonproduction, and put locks on resources nobody should change in a hurry. Run mode controls whether it asks. RBAC controls what it can reach. You need both.

An example: the renamed environment

Back to the 2 a.m. failure. The login step fails because no federated credential matches the token's subject. (I walk through why that happens in my post on passwordless deployments.) A good agent run looks like this:

  1. Read the failed run and recognize an authentication failure, not a Terraform error.
  2. Compare the job's environment name with the subjects on the managed identity's federated credentials.
  3. Find the recent commit that renamed the environment.
  4. Open a pull request that updates the federated credential in the platform Terraform, with the evidence in the description.

A person reviews and merges it, and the normal pipeline applies it. The agent saved forty minutes of digging. It didn't get to change identity configuration on its own, and it shouldn't.

A ladder of trust

  1. Ask. Read-only questions: what changed, why is this slow, what does this error mean. No approval needed.
  2. Propose. The agent writes up a diagnosis and a suggested fix. Nothing changes.
  3. Pull request. The fix arrives as code, through review and the normal pipeline.
  4. Act with approval. Review mode for direct changes, like restarting an app or scaling out.
  5. Act alone. Autonomous mode for one specific, repeated fix that you've approved many times, in nonproduction first.

Most of the value is in the first three rungs, and they carry almost no risk.

What agents still get wrong

  • Confident wrong answers. A fix that's right for most environments and wrong for yours. Always look at the plan or the diff before approving.
  • Missing context. Agents don't know the decision you made 18 months ago unless it's written down. Runbooks and decision records in the agent's knowledge base pay off quickly.
  • Blast radius. An agent fixes what you asked about. It doesn't feel that a change touches forty downstream services.
  • Injected instructions. Alerts, log lines and issue comments can contain text an attacker controls. An agent that reads them can be steered. This is another reason writes need a gate.

What the job becomes

The work moves up a level. Instead of reading every log, you design the observability the agent reads. Instead of writing every runbook step, you write the response plans and decide which ones get autonomy. Instead of fixing drift by hand, you decide which source of truth wins. And you review a lot more pull requests. Engineers who understand the systems underneath will be the ones who catch the agent when it's confidently wrong.

Where to start

  1. Turn on Azure Copilot for your team and use it for read-only questions for a few weeks.
  2. Set up SRE Agent on one nonproduction workload, with a tightly scoped identity, in Review mode.
  3. Connect your repositories so investigations can correlate with deployments.
  4. Let coding agents open pull requests on low-risk repositories, behind branch protection.
  5. Promote one repeated, well-understood fix to Autonomous mode, and see how it behaves.
