Healthcare Cloud on Azure: Designing for HIPAA and HITRUST

⏱ 7 min read 📅 October 8, 2025 ✍️ Srinivas Yenuganti
Healthcare HIPAA HITRUST CSF Azure PHI Compliance Architecture

When I design a platform that will hold protected health information (PHI), I try to make compliance a side effect of the architecture rather than a project at the end. If PHI can't reach the internet, every access is logged, keys are under your control and recovery is tested, the audit mostly becomes a matter of showing evidence. If those things are bolted on later, the audit becomes a remediation project.

This post walks through the Azure design I use for HIPAA-regulated workloads and how it lines up with HITRUST. Think of a typical example: a SaaS platform that takes in claims and clinical documents through APIs, stores them in Azure SQL and a data lake, and runs some analytics and Azure OpenAI processing on top.

What Azure covers, and what it doesn't

Microsoft offers a Business Associate Agreement (BAA) that covers a specific list of in-scope Azure services. Only build PHI workloads on services that appear on that list, and check it when you add something new. The list changes over time.

Azure Policy has a built-in HITRUST/HIPAA regulatory compliance initiative, and Microsoft Defender for Cloud can show HIPAA in its regulatory compliance dashboard. I turn both on early, at the highest scope that makes sense, because they show gaps months before an auditor does. But read Microsoft's own caveat: a "compliant" result only means the mapped policies pass. Many controls can't be checked automatically, so the dashboard is a partial view, not a certificate.

Classify the data before drawing anything

Not everything in a healthcare platform is PHI, and treating it all the same is expensive. I agree three classes up front:

ClassExamplesControls
PHINames with diagnoses, member IDs, claims, clinical notesBAA-covered services only, private endpoints, customer-managed keys, full audit logging, tight RBAC
De-identifiedData with identifiers removed under HIPAA's de-identification rulesStandard encryption; can feed analytics with lighter controls
OperationalMetrics and application logs that contain no PHINormal platform security

That third row is a promise you have to keep. Application logs are the most common place PHI leaks into a system nobody treats as sensitive. If logs might contain PHI, classify them as PHI.

Network: one way in, one way out

The rule I start from is simple: nothing that touches PHI has a public endpoint.

  • Inbound: a single Application Gateway WAF v2 is the only public entry point. Use the current Default Rule Set (DRS 2.2, which Microsoft now recommends over the older OWASP CRS 3.x sets), start in Detection mode to tune false positives, then switch to Prevention.
  • The spoke: App Service or containers with VNet integration, and every PaaS service (SQL, Storage, Key Vault, Service Bus, Azure OpenAI) reached through a private endpoint with public network access turned off. Enforce that with Azure Policy so "temporary" exceptions can't appear.
  • Outbound: a route table sends all egress to Azure Firewall in the hub, which only allows the destinations you've listed.
  • DNS: keep the private DNS zones central in the hub and link them, so every spoke resolves private endpoints the same way.
  • Admin access: Azure Bastion, never public RDP or SSH. DDoS Network Protection goes on the virtual network that holds the public IP.

Encryption and keys

Azure encrypts storage at rest by default with Microsoft-managed keys. For PHI I use customer-managed keys (CMK) in Key Vault. The main benefit is control: if you disable or revoke the key, the data becomes unreadable, which is also a clean way to end access when a customer leaves.

  • Put the key vaults in a separate security subscription, so someone with full rights on the workload subscription still can't touch the keys.
  • Turn on soft delete and purge protection. Storage CMK requires both anyway, and they stop a key from being destroyed by accident or on purpose.
  • Automate key rotation instead of relying on a calendar reminder.
  • In transit, require TLS 1.2 or later everywhere and HTTPS only on web apps, with certificates from Key Vault.

Identity: least privilege, and no standing admin

  • Applications use managed identities with data-plane roles, such as Storage Blob Data Reader, not Contributor or Owner.
  • People get admin rights through Microsoft Entra Privileged Identity Management, just in time and with approval, not permanently.
  • For any remaining VMs, use just-in-time VM access from Defender for Servers so management ports are closed by default.
  • Run access reviews on everything that touches PHI. HITRUST assessors will ask for the evidence.
  • Keep two cloud-only break-glass accounts protected with FIDO2 keys, and alert on every sign-in from them.

Audit logging and how long to keep it

HIPAA expects you to be able to show who accessed PHI and what changed. In Azure that means collecting:

  • The Azure activity log for every subscription.
  • Microsoft Entra sign-in and audit logs.
  • Resource logs for everything that touches PHI: SQL auditing, Storage access logs, Key Vault audit events, App Service HTTP logs, Azure Firewall and WAF logs. Remember that resource logs aren't collected until you create diagnostic settings.
  • Network flow logs for the PHI virtual networks.

On retention, a correction to something I see repeated a lot: HIPAA requires you to keep required documentation, such as policies and records of required actions, for six years. It doesn't set a specific number of days for every log. Many organizations keep audit logs for six years to be safe, and that's what I usually plan for. Agree the actual number with your compliance team and write down why. I keep recent data queryable in Log Analytics and send a long-term copy to blob storage with an immutability policy, so nobody can quietly edit or delete it.

Backup and disaster recovery

HIPAA requires a contingency plan, and an untested plan isn't one. The building blocks:

  • Azure SQL failover groups for regional failover. Microsoft documents a typical recovery time under 60 seconds. Data loss depends on how much hadn't replicated yet when the region failed, so don't promise zero.
  • Geo-redundant storage (RA-GRS or RA-GZRS) for critical blobs, so they're readable from the secondary region.
  • Azure Backup with soft delete and immutable vaults for VMs and databases, so backups survive a compromised admin account.
  • A DR drill at least once a year, with written results. Fail the whole application over, not just the database.

Mapping controls for the auditor

Auditors want to see the line from a requirement to something you built. This is the kind of table I keep in the design document:

Encryption§164.312(a)(2)(iv), (e)(2)(ii)Customer-managed keys in Key Vault, TLS 1.2+
Audit controls§164.312(b)Diagnostic settings, Sentinel, immutable log archive
Integrity§164.312(c)(1)Immutable storage, change tracking, Defender for Cloud

Map the matching HITRUST CSF requirements from your assessment scope, since the exact control references depend on the CSF version and the assessment type you're pursuing.

Bake it into code

If you can't redeploy it, you can't really defend it. Here's a storage account baseline for PHI in Terraform. Note the identity block: the customer-managed key needs an identity that can read the key, and leaving it out is a common reason this fails.

resource "azurerm_storage_account" "phi" {
  name                              = var.storage_account_name
  resource_group_name               = var.resource_group_name
  location                          = var.location
  account_tier                      = "Standard"
  account_replication_type          = "RAGRS"
  min_tls_version                   = "TLS1_2"
  https_traffic_only_enabled        = true
  allow_nested_items_to_be_public   = false
  public_network_access_enabled     = false  # private endpoints only
  infrastructure_encryption_enabled = true   # second layer of encryption

  identity {
    type         = "UserAssigned"
    identity_ids = [azurerm_user_assigned_identity.storage.id]
  }

  customer_managed_key {
    key_vault_key_id          = azurerm_key_vault_key.cmk.id
    user_assigned_identity_id = azurerm_user_assigned_identity.storage.id
  }

  tags = { "data-classification" = "phi" }
}

Two notes on that example. Microsoft says most workloads don't need infrastructure encryption, so include it only if your compliance requirements ask for double encryption. And it can only be turned on when the account is created, so decide before the first deployment. Also, when you set up a customer-managed key at creation time, Azure requires a user-assigned identity, which is why the example uses one.

Mistakes I see most often

  • A public endpoint on SQL or Storage "just for the migration" that's still there a year later.
  • Connection strings and keys in app settings or pipelines instead of managed identities.
  • PHI in application logs that are stored and shared as if they were harmless.
  • No diagnostic settings on Key Vault or SQL, discovered during the audit.
  • Contributor or Owner on application identities.
  • A DR plan nobody has ever run.
  • No data-flow diagram, so nobody knows every place PHI ends up.

Where to start

  1. Draw the data flow and classify every store as PHI, de-identified or operational.
  2. Assign the HITRUST/HIPAA initiative and the Defender for Cloud HIPAA standard, and read the gaps.
  3. Remove public endpoints from everything that holds PHI and enforce it with policy.
  4. Move keys and logs into a separate security subscription, with CMK and diagnostic settings everywhere.
  5. Run a DR drill and write down what happened.

Get classification and network isolation right first. Most of the other controls fall into place around them.
