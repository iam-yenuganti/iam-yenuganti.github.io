Healthcare Analytics on Microsoft Fabric, with AI from Microsoft Foundry

⏱ 8 min read 📅 May 16, 2026 ✍️ Srinivas Yenuganti
Microsoft Fabric Healthcare HIPAA Microsoft Foundry OneLake

Healthcare data is usually spread across an EHR, a claims system, imaging archives and a pile of flat files, none of which were designed to work together. Microsoft Fabric gives you one place to bring it together, and Microsoft Foundry gives you the models. The hard part isn't wiring them up. It's doing it in a way you can defend to a privacy officer and an auditor.

This is the design I'd use for a healthcare analytics platform on Fabric, with AI added carefully at the end.

Start with healthcare data solutions, not an empty lakehouse

Healthcare data solutions in Microsoft Fabric deploys the bronze, silver and gold lakehouses and the pipelines between them. You get FHIR ingestion, DICOM metadata transformation, an OMOP Common Data Model (v5.4) in gold, and optional transformations such as CMS claims in CCLF format. Building that yourself is months of work that doesn't differentiate anyone.

One detail I like: when FHIR resources move from bronze to silver, the pipeline replaces each resource ID with a deterministic hash of the original ID, the source system and the resource type, and keeps the original in its own column. That gives you globally unique IDs across source systems without losing lineage back to the source.

Not everything fits the built-in pipelines. Raw X12 837 and 835 claim files, for example, need your own parsing pipeline into bronze. Check what's covered before you plan the work.

What each layer is for

  • Bronze holds data exactly as received. Only pipeline identities can read it. Nobody runs reports here.
  • Silver holds validated, flattened FHIR with the deterministic IDs. Data engineers work here, and access is still tightly limited because it's full of PHI.
  • Gold holds OMOP tables and purpose-built marts, de-identified wherever the use case allows. This is what analysts and Power BI see.
  • Power BI reads gold through Direct Lake, with row-level security by facility or department and sensitivity labels on the reports.

The rule I hold to: the further right you go, the fewer identifiers and the more people. If a report needs names, that's a deliberate, approved exception, not the default.

Network and keys

Fabric now has workspace-level controls that make a PHI workspace much easier to lock down:

  • Workspace private links restrict inbound access to approved virtual networks.
  • Outbound access protection blocks all outbound connections from the workspace by default. You then allow specific destinations with managed private endpoints (for Data Engineering and OneLake) or data connection rules (for Data Factory). It needs an F SKU capacity and a tenant admin to enable the setting.
  • Customer-managed keys encrypt the workspace's data, including OneLake, with your key in Key Vault or Managed HSM. The vault needs soft delete and purge protection. If you revoke the key, access to the data is blocked within about an hour.

Check the security feature availability table before you design around these. Support varies by item type. When I last checked, in November 2026, healthcare data solutions supported customer-managed keys but not workspace private links, so the network design has to account for that.

Audit who read what

Fabric records user activity in the Microsoft Purview audit log, and you search it from the Purview portal. For HIPAA's audit control requirement, that's the evidence trail: who opened which item, when. I export those events to the SIEM and alert on unusual access, such as someone reading a PHI-labeled dataset they've never touched before, at 3 a.m.

If you use Fabric data agents, their prompts and responses can also be captured in Purview (in preview). That matters, because a chat question can reveal as much as a query.

Add AI behind a de-identification step

Good first AI use cases on this platform are modest and measurable:

  • Turning unstructured clinical notes into structured fields such as problem, medication and follow-up.
  • Scoring claims for denial risk before submission.
  • Letting analysts ask questions of gold data in plain language through a Fabric data agent.

For anything that sends text to a model, I remove identifiers first. Even with a private endpoint and a business associate agreement in place, I'd rather the model never sees a name or a medical record number it doesn't need. Outputs come back as new columns or tables in gold, with lineage to the source records.

Two current details if you connect Fabric to Foundry agents. First, the Foundry tool that called Fabric data agents directly is retiring on November 6, 2026, replaced by the Fabric IQ tool, so migrate any agents still using it. Second, Microsoft notes that responses returned to Foundry may leave Fabric's compliance boundary or region and fall under Foundry's data handling terms. Make sure that's acceptable for the data involved before you connect anything.

Order of work

  1. Provision an F SKU capacity and a dedicated production workspace for PHI.
  2. Turn on the network controls the items you use support, plus the customer-managed key.
  3. Deploy healthcare data solutions and ingest a sample before real data.
  4. Set up Purview auditing and SIEM export, and test that you can answer "who read this?"
  5. Build gold marts and Power BI reports with row-level security.
  6. Add AI last, one use case at a time, behind de-identification.

Fabric removes a lot of plumbing. It doesn't remove the need to decide, for each dataset and each person, how much they really need to see.
