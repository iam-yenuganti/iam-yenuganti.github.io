Making Defender for Cloud Findings Actually Get Fixed

7 min read · 25 September 2026

A security recommendation isn't a fix. I've seen plenty of setups where every pull request passes its checks, Defender for Cloud still flags the deployed resource, and the finding sits in a dashboard because the security team can see it but can't change it, and the team that could change it never sees it.

Connecting GitHub to Microsoft Defender for Cloud helps, but the tool isn't the hard part. The hard part is a loop: every finding reaches someone who can fix it, the fix goes through the normal pipeline, and someone checks that the deployed resource actually changed. Here's how I set that up.

Start with ownership, not scanners

Before deciding what should block a build, write down a small record for each service: name, owning team, application and infrastructure repositories, Azure subscription and resource group, and who to escalate to. It's a spreadsheet's worth of data, and it's the difference between a finding landing with the right team and bouncing around for a week.

Shared infrastructure needs an explicit owner too. A misconfigured hub network belongs to the platform team even if every application runs on it. "Unmapped" must never mean "unowned".

Connect GitHub, then check what you actually got

You onboard from Environment settings in Defender for Cloud by adding a GitHub environment. That creates a connector in an Azure subscription and installs the Defender for Cloud GitHub app on your organization. You need Contributor on the subscription and Organization Owner in GitHub. If someone only needs to read the findings, Security Reader on the connector's resource group is enough.

Three things are easy to get wrong:

  • Discovery takes time. Repositories can take up to eight hours to appear in Inventory and DevOps security.
  • Discovery isn't scanning. A repository showing up means Defender knows it exists. Code, secret, dependency and IaC scanning results need the Microsoft Security DevOps action configured in the workflow.
  • The app's repository access matters. Microsoft recommends giving it access to all repositories. If you limit it, write down which ones are excluded so nobody reads an empty result as a clean one.

Pick one representative repository, confirm findings arrive, and only then roll out further.

Know which plan you're on

The free Foundational CSPM plan gives you recommendations and secure score. The features that make this loop work well, such as code-to-cloud mapping, attack path analysis and pull request annotations, need the paid Defender CSPM plan. Pull request annotations in GitHub also require GitHub Advanced Security. Check both before you design a process around those features.

Secure score is a useful trend line. It isn't a release approval, and it isn't proof of compliance with any particular regulation.

Two places to catch problems

In the pull request, while the author still remembers why they wrote the change. Scan for secrets, code issues, vulnerable dependencies, IaC misconfigurations and container image problems.

After deployment, the question changes from "is this change safe?" to "what's actually exposed right now?" That's where Defender's posture findings and attack paths help, because they reflect the real environment, including things no pull request touched.

Where code-to-cloud mapping is available, use it to suggest which repository and team own a resource, then confirm against your service records. Shared clusters and base images often have more than one owner, and the mapping won't always know that.

Block, warn or investigate

Blocking every finding trains people to bypass the checks. Ignoring them turns the dashboard into a graveyard. I agree a short decision table with the teams that run the service. This is team policy, not a Defender default:

DecisionWhenWhat happens
BlockA new, confirmed, high-confidence exposure in the service being changed, with no mitigationFix before release, or get a named, time-limited exception
WarnA real issue with limited impact and a documented compensating controlRelease goes ahead; an owned work item gets a target date
InvestigateA stale, unclear or unmapped findingConfirm the resource and owner before deciding

Exceptions are scoped to one service and one environment, and they expire. Never turn off a scanner for the whole organization to unblock one deployment. If a check is too noisy to block on, run it as a warning while you improve it.

Closing the loop

Take a finding on a production container app. The steps I expect:

  1. Confirm the resource and that the exposure is real.
  2. Find where its configuration lives: the service repository or a central infrastructure repository.
  3. Fix it there, through the normal pipeline.
  4. Deploy, and check that the resource changed.
  5. Look at the Defender recommendation again, allowing for its refresh interval, and only then close the ticket.

Closing the ticket when the pull request merges leaves half the loop open. I've seen fixes merge and never deploy.

I track two numbers separately: time from detection to an assigned owner, and time from assignment to a verified fix. If the first is slow, routing is the problem. If the second is slow, it's capacity or the pipeline.

Evidence for reviews

For anything material, keep the chain: the recommendation, the decision and who made it, the commit, the deployment, and the later check. When an auditor or reviewer samples a finding, they should be able to see who accepted any remaining risk, when that acceptance expires, and whether the scanner actually covered that repository.

Every quarter or so, reconcile the GitHub organizations, discovered repositories, Azure resources and your service records. A repository Defender never discovered will never have findings, and that silence isn't good news.

Rolling it out

  1. Pick one service. Map its repositories, resources and owners, and check your Defender plan.
  2. Connect the GitHub organization, wait for discovery, and confirm scanning works in one workflow.
  3. Route findings to owners for a few weeks before gating anything.
  4. Turn on blocking for a small set of high-confidence risks, with exceptions that expire.
  5. Verify deployed fixes and keep the evidence. Expand to the next service only when the first one works.
