Azure Container Apps, AKS or App Service: How I Choose

8 min read · 30 September 2026

"Should this run on AKS?" is one of the most common questions I get from application teams. Most of the time the honest answer is no. Azure Container Apps covers a large share of container workloads without anyone having to run a Kubernetes cluster. It's not the right answer every time, though, and it has one security gotcha that catches people out. Here's how I decide, and what I lock down when Container Apps wins.

What Container Apps actually gives you

Container Apps runs on Kubernetes, but you never see the cluster. You get the useful parts as managed features:

  • Event-driven scaling through KEDA, including scale to zero for HTTP and queue-driven apps.
  • Revisions and traffic splitting, so a canary release is a setting rather than a project.
  • Built-in ingress with managed certificates, internal-only if you want it.
  • Jobs that run on demand, on a schedule, or when events arrive.
  • Dapr for service-to-service calls and pub/sub, if your teams want it.

What you give up is the Kubernetes API. No custom operators, no CRDs, no node tuning, no choosing your own storage classes.

How I choose

If the workload...I pickWhy
Is an API or microservice with spiky or event-driven trafficContainer AppsScales on HTTP or queue length, scales to zero, no cluster to patch
Is a batch or scheduled taskContainer Apps jobsPay while it runs, no idle replicas
Needs operators, CRDs, a service mesh you control, or node-level settingsAKSOnly AKS gives you the Kubernetes API
Is a classic web app or API that doesn't need to be a containerApp ServiceDeployment slots, mature tooling, least to learn
Is a single short-lived container you orchestrate yourselfContainer InstancesA building block, not a platform

One detail changes the cost picture. Scale to zero only works with HTTP, TCP or event-based scale rules. If you scale on CPU or memory, the app can't go below one replica, so an always-on service on Container Apps costs about what you'd expect for always-on compute. For steady workloads, a Dedicated workload profile is often cheaper than Consumption.

The RBAC gotcha: "Operator" roles can read your secrets

This is the part I'd want every platform team to know. Several built-in roles use wildcard actions, and those wildcards include the listSecrets operation, which returns secret values in plain text:

  • Container Apps Contributor and Container Apps Operator, through Microsoft.App/containerApps/*/action
  • Container Apps Jobs Contributor and Container Apps Jobs Operator, through Microsoft.App/jobs/*/action

The role names sound operational. Their permissions are broader than that. So if you hand the Jobs Operator role to a support team so they can restart a job, you've also let them read every secret on it.

A custom role without the wildcard is better, but it isn't the whole fix. Starting a job accepts an execution template that can override the image, command and environment variables. Anyone who can start a job and knows a secret's name can run their own container, reference that secret and read it, and can use any managed identity available to the job. Microsoft's guidance is to treat "can start this job" as "can use this job's secrets and identities".

Here's a narrower custom role for people who only need to watch and stop jobs:

{
  "Name": "Container Apps Job Viewer and Stopper",
  "IsCustom": true,
  "Actions": [
    "Microsoft.App/jobs/read",
    "Microsoft.App/jobs/executions/read",
    "Microsoft.App/jobs/execution/read",
    "Microsoft.App/jobs/stop/action",
    "Microsoft.App/jobs/stop/execution/action",
    "Microsoft.App/managedEnvironments/read"
  ],
  "NotActions": [],
  "AssignableScopes": ["/subscriptions/<subscription-id>/resourceGroups/rg-app-prod"]
}

I leave start/action out on purpose. Only identities you'd trust with the job's secrets should be able to start it.

Two more habits reduce the damage if a role is too broad. Store secrets in Key Vault and reference them from the app through a managed identity, rather than pasting values into Container Apps. And if you discover an overly broad assignment, remove it and rotate the secrets it could reach.

Environments and networking

A Container Apps environment is the boundary for networking and logs, so I use separate environments for production and non-production, never one shared environment with naming conventions. For anything internal, deploy the environment into your own virtual network with internal-only ingress. Workload profile environments also support user-defined routes, so egress can go through the same hub firewall as the rest of your platform.

Images come from a private Azure Container Registry, pulled with a managed identity rather than registry passwords. Releases go through the pipeline, and a new revision only receives traffic after it passes its health checks.

What to watch in production

  • Replica counts and scale events. Slow scale-out during a traffic spike shows up as latency long before it shows up as errors. Set a sensible minimum replica count for latency-sensitive APIs.
  • Job outcomes. Track failed and long-running executions, not just whether the job started.
  • Role assignments. Review who holds the Container Apps roles above. It's a quick query and it catches the gotcha before an auditor does.

Where to start

  1. Pick one event-driven or batch workload that doesn't need the Kubernetes API.
  2. Deploy it into a non-production environment in your own virtual network, with secrets from Key Vault.
  3. Replace any broad Container Apps role assignments with narrow custom roles.
  4. Move it to production, then decide on the next workload based on what you learned.
