Zero Trust on Azure, in the Order I'd Do It

⏱ 8 min read 📅 November 14, 2025 ✍️ Srinivas Yenuganti
Azure Zero Trust Microsoft Entra ID Security Architecture Microsoft Sentinel

"Zero Trust" gets used so loosely that it's easy to forget it's a simple idea. Don't trust a request because of where it comes from. Check who's asking, from what device, for what, every time. Give them the least access that works. And assume something is already compromised, so you'd better be able to see it.

On Azure, none of that is one product you switch on. It's a set of decisions across identity, network, data and monitoring. This is the order I work through them, and what I consider the minimum for each.

Start with identity

Most real attacks start with a stolen or guessed credential, not a network exploit. So identity is where I spend effort first.

Conditional Access

Conditional Access is the policy engine in Microsoft Entra ID. Every sign-in is checked against your policies before a token is issued. My baseline:

  • MFA for everyone, and phishing-resistant MFA (passkeys, FIDO2 keys or certificate-based authentication) for anyone with admin rights.
  • A compliant or Entra-joined device for access to anything sensitive.
  • Legacy authentication blocked. It can't do MFA, so it's a way around everything else.
  • Sign-in risk and user risk policies that require stronger verification or block access when Entra sees something suspicious.

Run new policies in report-only mode for a couple of weeks first. You'll find the service account nobody documented and the team that still uses an old mail client, and you'll find them before they find you.

No standing admin access

Nobody should be Global Administrator or subscription Owner all the time. Make people eligible for those roles in Privileged Identity Management, and have them activate the role for a few hours with MFA, a reason and, for the most powerful roles, an approval. Pair it with regular access reviews so eligibility doesn't quietly pile up.

Workload identities

Applications authenticate with managed identities, not service principals with secrets in config files. Then give each identity the narrowest role that does the job. A function that reads blobs needs Storage Blob Data Reader, not Contributor.

Then the network

The goal isn't a perfect perimeter. It's making sure that when something is compromised, it can't reach much.

No public endpoints on data services

Storage accounts, Azure SQL, Key Vault, Service Bus, Container Registry: anything holding sensitive data should be reachable only through a private endpoint, with public network access disabled. I enforce this with Azure Policy at the management group level, so a new resource can't quietly come up with a public endpoint.

One inspected way in, one inspected way out

Web traffic comes in through Application Gateway with WAF v2 in prevention mode. Outbound traffic from workloads goes through Azure Firewall in the hub. Azure Firewall Premium adds signature-based intrusion detection and prevention (Microsoft lists more than 67,000 signatures), TLS inspection and full URL filtering. Standard is enough for many workloads; I use Premium where a regulation or the data really calls for traffic inspection.

Prefer application rules with FQDNs over network rules with IP ranges. Cloud IP addresses change, and "allow this destination by name" is easier to review than a list of addresses.

Segment inside the network too

Put NSGs on every subnet with a deny-by-default inbound posture, and use application security groups so rules say "web tier to app tier" rather than listing IP addresses.

For admin access to virtual machines, use Azure Bastion. No VM should have RDP or SSH open to the internet.

Protect the data itself

Secrets, keys and certificates live in Key Vault, with Azure RBAC for access, purge protection turned on, and no public network path. Azure RBAC is now the default for new vaults; access policies still work but are the legacy model.

Azure encrypts data at rest by default. Customer-managed keys give you control over the key and its rotation, and if you revoke the key, the service can no longer decrypt the data. That's useful for regulated data and for offboarding, but it also means a mistake with the key becomes an outage, so treat key access as seriously as data access.

Assume breach, so make sure you'd notice

"Assume breach" means nothing if a breach would be silent.

  • Microsoft Defender for Cloud for posture recommendations and threat detection on the resources you run. Enable the plans that match your workloads rather than everything by default; each plan has a cost.
  • A Log Analytics workspace collecting Entra sign-in and audit logs, the Activity Log, firewall, WAF and Key Vault logs. Keep data you need for investigations in the analytics tier, and use the workspace's long-term retention (up to 12 years) for compliance, instead of exporting logs to a storage account.
  • Microsoft Sentinel on top for detection and response: impossible travel, password spray, unusual Key Vault access, bulk downloads. Turn on UEBA so it learns what normal looks like for each user. Plan to run Sentinel in the Microsoft Defender portal; after March 31, 2027 it's no longer supported in the Azure portal.

A checklist I use in design reviews

  1. Phishing-resistant MFA for every privileged account
  2. MFA for all users through Conditional Access
  3. Legacy authentication blocked
  4. No standing admin roles; PIM for all of them
  5. Managed identities for workload authentication, with narrow roles
  6. Public network access disabled on data services; private endpoints only
  7. Inbound web traffic through WAF v2 in prevention mode
  8. Outbound traffic through Azure Firewall
  9. NSGs on every subnet, deny by default
  10. Azure Bastion for VM administration, no public RDP or SSH
  11. Secrets, keys and certificates only in Key Vault, with purge protection
  12. Defender for Cloud plans enabled for the workloads you run
  13. Sentinel connected to Entra, Activity Log and Defender, running in the Defender portal
  14. Access reviews scheduled, and secure score reviewed regularly

Where to start

Don't try to do all of this at once. Identity first: Conditional Access and PIM close the most common attack paths. Then the network: private endpoints and a firewall in the hub. Then detection. Each step makes the next one easier, and each is worth having on its own.
