Azure Application Gateway WAF: Common Mistakes and a Safer Rollout

⏱ 11 min read 📅 June 27, 2026 ✍️ Srinivas Yenuganti
Application Gateway WAF v2 OWASP CRS Healthcare HIPAA HITRUST FHIR Terraform

Application Gateway with WAF is the front door for most Azure SaaS apps I look at, and it's also the component I most often find misconfigured. The story is nearly always the same:

  1. Someone deploys the WAF in Prevention mode on day one to tick the security box.
  2. Within days it blocks real traffic: JSON bodies, file uploads, SSO callbacks.
  3. Someone switches it to Detection mode "for now".
  4. A year later it's still in Detection. The architecture diagram says WAF; nothing is actually being blocked.

The fix isn't a different product. It's a rollout that's slow at the start so it can be strict at the end. Here are the mistakes I see most, the design I aim for, and the steps I use to get from no WAF to Prevention without breaking users. At the end there's a section for healthcare workloads, where a WAF mistake is also a compliance problem.

The mistakes I see most often

  • Prevention on day one with no idea what normal traffic looks like.
  • Detection forever after the first bad day. That's logging, not protection.
  • Turning off whole rule groups, such as all SQL injection rules, instead of excluding one field from one rule.
  • Broad global exclusions that skip inspection of every argument for every rule.
  • No diagnostic logs, so nobody can tune anything.
  • One policy for every app on the gateway, so tuning one app weakens all of them.
  • Different SKUs per environment: Standard_v2 without WAF in test, WAF_v2 in production. Nothing you learn in test carries over.
  • HTTP to the backend, so traffic is unencrypted after the gateway.
  • Backends still reachable directly, which makes the WAF optional for anyone who finds the other address.
  • No autoscaling, so the first busy day turns into 502 errors.

What good looks like

The pieces that matter:

  • One ingress. The gateway is the only way in. Backends use private endpoints or internal load balancers and accept traffic only from the gateway subnet.
  • The current ruleset. Microsoft recommends Default Rule Set (DRS) 2.2 for new deployments. It's based on OWASP CRS 3.3.4 plus Microsoft's own threat intelligence rules. CRS 3.2 is still supported, but I wouldn't start a new policy on it.
  • Policies at the right scope. A WAF policy can be attached to the whole gateway, to a listener, or to a path rule. Exclusions in a policy apply to everything that policy covers. If the API needs an exclusion, put it in a policy for the API listener, not in the gateway-wide one.
  • End-to-end TLS with the certificate in Key Vault, read by the gateway's managed identity.
  • Autoscaling with a sensible minimum, so you're not caught out by a traffic spike.

The rollout, step by step

Step 1
Deploy in Detection
DRS 2.2, Detection mode, diagnostic logs flowing to Log Analytics from the first minute.
Step 2
Watch real traffic
Two to four weeks, so you see month-end jobs, releases and unusual clients. Review the top rule hits regularly.
Step 3
Tune narrowly
For each false positive, exclude the one field from the one rule, in the policy for that app only. Test in a non-production gateway.
Step 4
Switch to Prevention
One listener at a time, lowest risk first. Watch blocks closely for the first week.

Put the Prevention date in the change record when you start. "Detection for now" without a date is how step 4 never happens.

It also helps to understand anomaly scoring. With DRS, a matching rule doesn't block on its own; it adds to a score, and a request is blocked in Prevention mode once the score reaches 5. That's why the logs show rules as "Matched", followed by a separate "Blocked" or "Detected" entry for the request as a whole.

Tuning without weakening the WAF

Start with data. If you send logs to resource-specific tables, which I recommend, this shows what's firing:

// Top WAF rule hits over the last 7 days
AGWFirewallLogs
| where TimeGenerated > ago(7d)
| where Action in ("Matched", "Detected", "Blocked")
| summarize hits = count() by RuleId, RequestUri, Action
| top 50 by hits

Then exclude as little as possible. Here, rule 942100 fires on a JSON search field called filter, so I exclude only that argument from only that rule:

# Terraform (azurerm): one argument, one rule, in the API listener's policy
managed_rules {
  managed_rule_set {
    type    = "Microsoft_DefaultRuleSet"
    version = "2.2"
  }

  exclusion {
    match_variable          = "RequestArgNames"
    selector                = "filter"
    selector_match_operator = "Equals"
    excluded_rule_set {
      type    = "Microsoft_DefaultRuleSet"
      version = "2.2"
      rule_group {
        rule_group_name = "SQLI"
        excluded_rules  = ["942100"]
      }
    }
  }
}

What I don't approve: switching off a whole rule group, or an exclusion with no rule set attached, which skips that field for every rule. Both make the false positive go away by making the WAF stop looking.

I also stop people calling exclusions "whitelisting". You're not allowing traffic. You're telling one rule to ignore one field. Framing it that way makes the security review much shorter.

Monitoring that's worth having

Detection mode is only useful if someone reads the results. The alerts I set up first:

  • A sudden jump in hits for a single rule. Either someone's probing you or a release introduced a false positive.
  • Blocked requests above a small percentage of traffic for a backend.
  • Backend health probe failures, which are easy to mistake for WAF blocks during an incident.
  • Certificate expiry inside 30 days.
  • The gateway hitting its autoscale maximum.

Send the logs to Microsoft Sentinel or your SIEM, where they can be correlated with sign-in logs and application logs. On their own they're mostly noise.

Exclusions need to expire

Every exclusion is a gap in the ruleset. One added two years ago for an endpoint that no longer exists is just a gap. I keep exclusions in code, each with an owner and a review date. At each quarterly review, anything past its date is removed unless someone shows it's still needed. If the false positive comes back, it gets added again with fresh evidence.

A Terraform baseline

Deploy the same policy to every environment. Tuning done only in production is never tested, and exclusions added in the portal disappear at the next deployment.

# WAF policy: start in Detection, switch with a variable
resource "azurerm_web_application_firewall_policy" "baseline" {
  name                = "wafp-${var.app}"
  resource_group_name = var.rg
  location            = var.location

  policy_settings {
    enabled                     = true
    mode                        = var.waf_mode   # "Detection" until the baseline is done
    request_body_check          = true
    max_request_body_size_in_kb = 128
    file_upload_limit_in_mb     = 100
  }

  managed_rules {
    managed_rule_set {
      type    = "Microsoft_DefaultRuleSet"
      version = "2.2"
    }
  }
}

# Gateway: WAF_v2 SKU, autoscale, certificate from Key Vault
resource "azurerm_application_gateway" "this" {
  name                = "agw-${var.app}"
  resource_group_name = var.rg
  location            = var.location
  firewall_policy_id  = azurerm_web_application_firewall_policy.baseline.id

  sku {
    name = "WAF_v2"
    tier = "WAF_v2"
  }

  autoscale_configuration {
    min_capacity = 2
    max_capacity = 10
  }

  ssl_certificate {
    name                = "tls-cert"
    key_vault_secret_id = azurerm_key_vault_certificate.tls.versionless_secret_id
  }

  # ... identity, listeners, backend pools, HTTPS backend settings ...
}

Using the versionless secret ID lets the gateway pick up a renewed certificate on its own. Pair this with an Azure Policy assignment at the management group that requires WAF on every Application Gateway, so a gateway without one can't be deployed.

If the gateway carries health data

For healthcare APIs, everything above still applies, and a few things become compliance questions rather than good practice.

Watch what ends up in your logs

WAF logs include the request URI and the piece of the request that matched a rule. If identifiers sit in the URL, like /Patient/12345, or matched data contains patient details, that information is now in Log Analytics and every system that log feeds. That's a new copy of sensitive data with its own access model.

Two things help:

  • Log scrubbing on the WAF policy. It replaces values with asterisks for named request headers, cookies, query arguments, form fields and JSON fields, and it can remove client IP addresses. It doesn't scrub values inside the URL path, so identifiers in the path still get logged.
  • Treat the workspace as sensitive whatever you scrub: tight RBAC, private access where you can, and retention set by your compliance policy. Long-term retention in the workspace covers multi-year requirements without exporting logs elsewhere.

How the gateway supports HIPAA technical safeguards

SafeguardWhat the gateway setup contributes
Access control (§164.312(a))Single ingress, private backends, nothing reachable around the WAF
Audit controls (§164.312(b))Access and firewall logs in a protected workspace, retained per policy
Transmission security (§164.312(e))TLS 1.2 or later at the listener and HTTPS to every backend

The gateway doesn't make you compliant on its own; it's one part of the evidence. But "WAF in Detection mode" or "plaintext to the backend" are the kinds of findings that are easy to avoid.

Limit where traffic can come from

If the service only serves one country, a custom geo rule cuts out a lot of noise before the managed rules even run. Custom rules are evaluated first:

# Block everything not from the US
custom_rules {
  name      = "geoAllowUsOnly"
  priority  = 10
  rule_type = "MatchRule"
  action    = "Block"

  match_conditions {
    match_variables {
      variable_name = "RemoteAddr"
    }
    operator           = "GeoMatch"
    negation_condition = true
    match_values       = ["US"]
  }
}

Check your partners and integrations before you turn this on. A payment provider or identity provider calling back from another region will be blocked too.

Checklist

  • WAF_v2 in every environment, DRS 2.2 on new policies.
  • Detection at launch, with a Prevention date in the change record.
  • Diagnostic logs to Log Analytics from day one, in resource-specific tables.
  • Exclusions scoped to one field and one rule, in the narrowest policy, kept in code with an owner and review date.
  • No disabled rule groups and no broad global exclusions.
  • Private backends that accept traffic only from the gateway.
  • End-to-end TLS, certificate from Key Vault.
  • Autoscaling, with an alert when the maximum is reached.
  • Azure Policy requiring WAF on every Application Gateway.
  • For sensitive data: log scrubbing, a protected workspace, and no identifiers in URL paths where you can avoid it.

The short version

Start in Detection, watch real traffic for a few weeks, tune narrowly, and switch to Prevention on a date you set at the start. Then keep pruning exclusions. A WAF that's been tuned and then left alone slowly turns back into a WAF that isn't doing much.
