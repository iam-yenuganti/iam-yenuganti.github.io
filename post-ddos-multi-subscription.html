Azure DDoS Protection: One Plan for Every Subscription

⏱ 9 min read 📅 June 28, 2026 ✍️ Srinivas Yenuganti
DDoS Protection Hub-Spoke Cost Optimization Landing Zone Healthcare HIPAA Terraform

Here's a pattern that shows up in a lot of multi-subscription Azure tenants. The platform team creates an Azure DDoS Protection plan in the connectivity subscription. Then a workload team in another subscription launches an internet-facing app, sees "enable DDoS protection" on their checklist, and creates their own plan. Another team does the same. A year later the tenant is paying for several plans that all provide exactly the same protection.

DDoS Network Protection is billed as a fixed monthly fee per plan, whether or not any virtual network is attached to it. And you only ever need one. Microsoft's documentation is direct about it: a single plan can protect virtual networks across multiple subscriptions, as long as they're in the same Microsoft Entra tenant.

This post covers how to set that up properly: the tier choice, the permissions, the Terraform, the policy that keeps it that way, and the operational side people skip.

One plan per tenant

A DDoS protection plan isn't really a subscription resource. It's a regional resource you can link to virtual networks in any region and any subscription under the same tenant. The plan's subscription gets the monthly bill, plus overage charges if you protect more than 100 public IP addresses across the tenant.

So the rule is simple: create exactly one plan, in the Connectivity subscription the platform team owns, and associate every virtual network that needs Network Protection with it.

Network Protection or IP Protection?

There are two paid tiers, and they suit different estates:

IP ProtectionNetwork Protection
ScopeIndividual public IP addressesVirtual networks linked to a plan
PricingPer protected public IPFixed monthly fee covering up to 100 public IPs, then overage
DDoS Rapid Response teamNoYes
Cost protection creditsNoYes
Application Gateway WAF discountNoYes, WAF billed at the non-WAF rate
FitsA handful of public IPsLarger or multi-subscription estates, regulated workloads

Microsoft's rough guidance is that IP Protection is cheaper below about 15 public IPs and Network Protection above that. Check current prices for your region before deciding. For a multi-subscription estate with regulated, internet-facing workloads, I'd choose Network Protection for the rapid response team and cost protection alone. The mistake isn't picking the wrong tier. It's buying Network Protection more than once.

Also remember what you get for free. Every Azure public IP already has DDoS infrastructure protection. It has no SLA, alerts or rapid response, which is fine for dev and test.

Permissions for cross-subscription association

Sharing the plan is a permissions problem, not a networking one. Whoever creates or updates a spoke virtual network needs Microsoft.Network/ddosProtectionPlans/join/action on the plan. That requirement doesn't go away after the first association; later updates to a protected virtual network need it too.

  • Grant it at the plan's scope, not the whole Connectivity subscription.
  • A custom role with just that action is the least-privilege option. Network Contributor on the plan works too but grants more.
  • Assign it to the deployment identities or groups that build spokes, through the same group-based model your landing zone already uses.

Terraform

The plan sits in the hub subscription. The spoke references it by resource ID through a second provider alias:

# One provider per subscription
provider "azurerm" {
  alias           = "hub"
  subscription_id = var.hub_subscription_id
  features {}
}

provider "azurerm" {
  alias           = "spoke"
  subscription_id = var.spoke_subscription_id
  features {}
}

# The only DDoS plan in the tenant
resource "azurerm_network_ddos_protection_plan" "tenant" {
  provider            = azurerm.hub
  name                = "ddos-plan-tenant"
  resource_group_name = var.hub_rg
  location            = var.location
  tags = {
    owner   = "platform-network"
    purpose = "tenant-wide-ddos-network-protection"
  }
}

# A spoke in another subscription, same tenant
resource "azurerm_virtual_network" "spoke" {
  provider            = azurerm.spoke
  name                = "vnet-spoke-app1"
  resource_group_name = var.spoke_rg
  location            = var.location
  address_space       = ["10.20.0.0/16"]

  ddos_protection_plan {
    id     = azurerm_network_ddos_protection_plan.tenant.id
    enable = true
  }
}

In practice the spoke usually lives in a different Terraform state, so pass the plan ID in as a variable or read it with a data source instead of referencing the resource directly.

Use policy to keep it that way

Good intentions fade. Two policy assignments at the intermediate root management group make the pattern stick:

  • The built-in policy "Virtual networks should be protected by Azure DDoS Protection" with the Modify effect, pointed at the shared plan. New virtual networks get associated automatically, and existing ones can be remediated.
  • A deny on creating Microsoft.Network/ddosProtectionPlans anywhere outside the Connectivity subscription.

Then add a recurring Azure Resource Graph query for plans that shouldn't exist and public IPs whose virtual network isn't protected. It takes minutes and it's usually where the waste turns up.

Operate it like a control, not a purchase

A DDoS plan nobody has tested is closer to a receipt than a control. What I set up from day one:

  • Diagnostic logs. Send DDoS protection notifications, mitigation flow logs and mitigation reports from each protected public IP to Log Analytics.
  • Alerts. Alert on the "Under DDoS attack or not" metric for each protected public IP, routed to whoever is on call.
  • Simulation. Run an attack simulation through one of Microsoft's approved testing partners at least once a year, and after major network changes.
  • Rapid response. Document how to engage the DDoS Rapid Response team in the incident runbook now, not during the attack.

A note for healthcare workloads

For healthcare SaaS, DDoS is an availability question before it's a cost question. A volumetric attack that takes a patient portal or a FHIR API offline is exactly the kind of event your HIPAA contingency plan (§164.308(a)(7)) is supposed to cover. A shared plan helps here: one association rule to evidence, one place the logs land, and a simulation result you can put in front of an auditor. Keep the DDoS logs in the same workspace and under the same retention as your other security logs.

Checklist

  • Exactly one DDoS Network Protection plan in the tenant, in the Connectivity subscription.
  • Spoke deployment identities hold ddosProtectionPlans/join/action on the plan only.
  • Policy at the intermediate root: Modify to protect virtual networks, and deny new plans elsewhere.
  • Diagnostic logs and attack alerts on every protected public IP.
  • A yearly simulation and a documented rapid response contact path.
  • A recurring query for extra plans and unprotected public IPs.
